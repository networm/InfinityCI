## Infinity-CI 与 Jenkins / TeamCity / GitHub Actions 横向对比

### 一、能力对比总表（✅=对齐 ⚠️=部分 ❌=缺失）

| 能力域 | Jenkins | TeamCity | GitHub Actions | Infinity-CI |
|---|---|---|---|---|
| 流水线定义 | Jenkinsfile(Groovy)+共享库 | Kotlin DSL+模板层级 | YAML+reusable workflows | ✅ YAML；❌ 无模板/复用 |
| 任务编排 | stages+parallel | Build Chain 快照/产物依赖 | needs DAG | ✅ needs DAG+级联跳过+always() |
| Matrix 组合构建 | matrix 轴 | matrix 参数 | matrix+fail-fast | ❌ |
| 条件/表达式 | when+Groovy 全量 | Kotlin 表达式 | if+表达式函数 | ⚠️ 仅 job 级 always() |
| 触发 | webhook/定时/上游/轮询 | VCS 触发+schedule+完成触发 | push/PR/schedule/dispatch/call | ⚠️ 手动+cron+签名 webhook；❌ PR 事件、上游触发、cron 时区、补跑 |
| 执行环境 | agent label+docker agent+云 | agent pool+云扩缩+容器 step | hosted/self-hosted | ✅ local/agent/label/并发槽/断线重排队；容器化按决策暂缓 |
| Artifact 产物 | archive+fingerprint | 一流（产物依赖） | upload/download-artifact+Release | ❌ |
| 缓存 | 插件 | 无原生 | actions/cache 原生 | ❌ |
| 测试报告 | junit 插件 | 一流（历史/失败首因/flaky 定位） | Checks+行内标注 | ❌ |
| SCM 深度集成 | 插件 | VCS root+checkout 规则 | 原生 status/checks/PR UI | ⚠️ git checkout+凭据+webhook；❌ commit status 回写、PR 事件、GitLab/Gitea 适配 |
| Secret 管理 | Credentials 体系 | 项目级 secret 参数 | Secrets/Environments/OIDC | ⚠️ 仅 Git 凭据加密存储 |
| 权限/审计 | RBAC 插件 | 细粒度+审计日志 | org 权限+审计 | ✅ 三级角色+项目可见性贯穿实时推送；❌ 审计日志 |
| 通知 | 插件生态 | 内置邮件+notifier | 无原生（用 marketplace） | ⚠️ 仅企业微信 |
| 保留/清理 | 插件 | 强（保留规则） | 90 天自动 | ❌ 永久累积 |
| 统计报表 | 插件 | 强（图表 tab） | Insights | ❌ |
| 实时日志 | 轮询控制台 | 实时 | 实时 | ✅ xterm.js+SignalR，达到三家水准 |
| 配置版本化 | Jenkinsfile 在业务仓 | 设置可 VCS 同步 | YAML 在业务仓 | ✅ 特色：独立 Git 配置仓+历史回滚+只读 clone |

### 二、结论

底座（多项目可见性、分布式 agent、实时推送、配置版本化、参数化构建、step 级重试/超时）已达到三家的基础水位；**最大空白集中在三类：① SCM 协作闭环（status 回写/PR 触发）、② 构建内核（artifact/cache/测试报告/表达式）、③ 治理（secret/审计/保留/报表）**。按你选定的方向，路线图以协作与集成为 P0，容器化暂不规划。

### 三、实施路线图

**P0 协作与集成（先行）**
1. **commit status 回写**（S/M）：GitHub Status API + GitLab pipeline status；run 入队置 pending、终态回写 success/failure；复用现有命名凭据做 token；`workflow.yml` scm 段加 `commit_status: true`。涉及 `GitSourceFetcher.cs`、新 `Scm/CommitStatusReporter.cs`、`RunQueueService` 终态钩子。
2. **PR/MR 事件触发**（M）：webhook 收包器解析 `pull_request`(opened/synchronize/reopened) 与 GitLab `merge_request` 事件；`workflow.yml` 增加 `on:` 触发器段（push 分支过滤已有，扩展 PR 动作过滤）；PR 编号/源分支注入 env 与 Run 记录。
3. **GitLab/Gitea webhook 适配**（S/M）：事件语义层识别 `X-Gitlab-Event`/Gitea 头与各自 secret 校验方式，统一转成内部 push/MR 事件模型。
4. **通知渠道扩展**（M）：抽 `INotifier` 接口（改造现有 `WeComNotifier`），新增 Email(SMTP)/钉钉/Slack/通用出站 webhook；每工作流可配多渠道+事件过滤（仅失败/全部）；自动化卡片 UI 扩展为渠道列表。

**P1 构建内核**
5. **Artifact**（M/L）：step 结果声明或 `artifact_upload` 段 → master 归档目录 → REST 上/下载 + 保留策略 + 运行页产物区 UI（参照 GHA）。
6. **Cache**（M）：`cache: key/restore-keys` 语义，目录打包按 hash 存取。
7. **测试报告**（M）：JUnit XML 解析入库 → 运行页 Tests 标签（用例表/失败摘要/历史趋势后置）。
8. **表达式引擎+step 级 if+outputs**（M/L）：最小函数集 `success()/failure()/always()/params()/env()`；job outputs 映射供 needs 下游引用。

**P2 治理与体验**
9. Secret 保险库+日志脱敏（M）；10. 审计日志（S）；11. 运行/日志/产物保留清理（S/M）；12. 统计报表（成功率/耗时/agent 利用率）（M）；13. 运行列表筛选搜索分页+YAML 编辑器高亮校验（M）；14. Matrix（M）；15. cron 时区+错过补跑（S）。

**不做**：容器化执行与 services（已决策暂缓，model 留扩展点）。

确认后从 P0-1（commit status 回写）开始实施。
