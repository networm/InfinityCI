# v6：任务优先重构（含数据库版本迁移，不重建、不丢数据）

## 0. 数据库版本迁移机制（新增基础设施）

- **版本表** `SchemaVersion`：`{ Id=1, Version int, AppliedUtc }`，记录当前数据库架构版本
- **迁移运行器** `DbMigrator`（启动时执行）：
  - 空库 → `EnsureCreated`（按当前模型建表）→ 版本号直接盖为最新
  - 存在旧库但无版本表 → **基线盖戳**（当前实际结构记为版本 5）→ 继续升级
  - 已有版本号 → 依序执行 `(fromVersion → toVersion)` 的迁移步骤列表直到最新
- **迁移以代码中的有序步骤定义**（每步 = 版本 + SQL/委托），未来变更只追加 `6→7、7→8…`，实现"从指定版本升到指定版本"
- 本轮新增迁移 **5→6**：`Runs` 表加 `RunNumber` 列（NOT NULL DEFAULT 0）→ 按任务回填编号（按 Id 顺序 1..n，历史数据保留且可查看）→ 建 `(WorkflowName, RunNumber)` 唯一索引
- 专测：构造 v5 形状库 + 旧数据 → 迁移 → 断言版本号、回填正确、数据未丢失

## 1. 运行编号任务内自增

- `Run.RunNumber` + 唯一索引 `(WorkflowName, RunNumber)`（见迁移）；内部 `Id` 保留作 JobRun 外键
- 触发时事务内 `MAX(RunNumber)+1`；Run 载荷携带 `runNumber`

## 2. 新路由：`/runs/{workflow}/{runNumber}`

- 任务作用域端点：`GET /api/jobs/{wf}/runs/{n}`（Run+Jobs）、`.../logs/{jobKey}`、`.../download`、`.../cancel`；原 `/api/runs/{id}` 保留兼容
- 触发响应含 `runNumber`；`/api/runs` 全局列表保留

## 3. 存储布局：先任务后类别，每任务一个独立 Git 仓库

```
data/
  {workflow}/
    workflow.yml
    .git/                 ← 该任务自己的版本仓库
    .gitignore            ← 忽略 logs/ workspaces/
    logs/{runNumber}/{jobKey}.jsonl
    workspaces/{runNumber}-{jobKey}/
```

- 任务创建时 `git init` + 写 `.gitignore`；历史/回滚/提交作用于该任务仓库；按任务克隆 `git clone http://user:pass@host:5000/git/{workflow}`（原全局 /git/jobs 移除）
- `JobLogStore`/工作区/`WorkflowStore`/`WorkflowGitStore` 全部改为任务作用域路径

## 4. 前端

- 路由 `/runs/$workflow/$runNumber`；Dashboard/Runs 列表/任务详情历史/触发跳转全部改用；列表显示任务内编号
- Run 详情页按 (workflow, runNumber) 拉取；任务名改为指向 `/jobs/{workflow}` 的链接
- 任务图：单步/无 needs 也渲染最小图；点击只高亮当前结点，连线不变色
- 任务页克隆提示改为按任务仓库
